# ホンダの諸元表・装備表の構造

- **日付**: 2026-08-31
- **対象**: ホンダ フィット（`fit_spec_list.pdf` / `fit_equipment_list.pdf`）
- **目的**: トヨタ2車種で作った取り込み経路が、他社でどこまで通るかを確かめる

トヨタ以外で最初に当たる壁を先に見るため、既存調査（2026-08-24）で
「さらに深刻」とされたホンダ フィットを選んだ。

## 結論の要約

| | トヨタ | ホンダ | 影響 |
|---|---|---|---|
| PDFのURL | 年月付き（`prius_spec_202607.pdf`） | **年月なしの固定**（`fit_spec_list.pdf`） | 対応済み（`url_kind`） |
| 諸元と装備 | 同じPDFの別ページ | **別のPDF** | 収集元を2つ持つ必要がある |
| ページ数・判型 | 6ページ / A3横 | 1ページ / A4縦（装備は2ページ） | 読み取りの手順が変わる |
| 装備の表現 | **色**（緑/橙/青/白） | **記号**（●◎） | **テキストで読める。画像処理が要らない** |
| 装備の粒度 | 1行1機能 | **1行が複数機能を覆う** | 表記辞書が「1行→複数列」を扱う必要がある |
| 寸法の単位 | mm（4,600） | **m（3.995）** | 変換が要る |
| 型式 | バリアントごとに一意 | **1つが複数バリアントを覆う** | 既知（複合キーで同定済み） |
| 価格 | JS描画のページ | JS描画のページ | 同じ（ブラウザで読む） |

**装備がテキストで読める点でホンダはトヨタより易しく、1行が複数機能を覆う点で難しい。**

## 発見1 諸元と装備が別のPDFにある

```
https://www.honda.co.jp/Fit/common/pdf/fit_spec_list.pdf       主要諸元（1ページ）
https://www.honda.co.jp/Fit/common/pdf/fit_equipment_list.pdf  主要装備（2ページ）
```

トヨタは1つのPDFの2〜5ページ目に装備一覧が入っているため、`spec_sources` は
車種につき1つの収集元を前提にしている。ホンダでは諸元と装備で別のURLになる。

`spec_sources` は車種に対して複数行を持てるので、2つ登録すれば収集自体は回る。
ただし `ingest-spec` は「最新の spec_document 1つ」に変更を紐づけるため、
どちらの書類に紐づけるかを決める必要がある。

## 発見2 装備は記号で表現されている（テキストで読める）

```
● は標準装備   ◎ はメーカーオプション
```

トヨタは色でしか表現しておらずテキスト抽出ではセルが空になるが、ホンダは
記号が文字として入っているため `pdftotext -layout` で読める。
**画像化・色判定の手順（`npm run read-equipment`）はホンダには要らない。**

つまり読み取り方はメーカーごとに違う。「色を判定する」を全社共通の手順に
してはいけない。

## 発見3【重要】1行が複数の装備を覆う

ホンダは運転支援をまとめて1行にする。

```
Honda SENSING（衝突軽減ブレーキ（CMBS）、誤発進抑制機能、後方誤発進抑制機能、
近距離衝突軽減ブレーキ、歩行者事故低減ステアリング、路外逸脱抑制機能、
渋滞追従機能付アダプティブクルーズコントロール（ACC）、車線維持支援システム（LKAS）、
トラフィックジャムアシスト、先行車発進お知らせ機能、標識認識機能、
オートハイビーム、パーキングセンサーシステム）        ● ● ● ● ● ● ● ●
```

この1行が、DBの列でいう `collisionMitigationBrake` / `falseStartSuppression` /
`laneDepartureWarning` / `laneKeepingAssist` / `adaptiveCruiseControl` の
**5列**を同時に埋める。トヨタは Toyota Safety Sense の中身を1行ずつ別の行に
分けて書くので、1行1機能で対応がついていた。

`lib/feature-vocabulary.ts` の `matchFeature` は当たった列を全部返す作りなので、
括弧の中の個々の名前を辞書に入れておけばこの形をそのまま扱える。
**1つに絞る作りにしていたら、ここで作り直しになっていた。**

## 発見4 寸法の単位が m である

```
全長（m）   3.995        ← トヨタは 全長 mm 4,600
全高（m）   1.515〈1.540〉
```

`dimensions` は mm の整数で持つ設計なので、3.995 → 3995 の変換が要る。
`〈〉` の意味（ルーフレール付きなどの別仕様）は未確認。

## 発見5 グレード名にパワートレインが入る

```
タイプ    e:HEV X    e:HEV Z    e:HEV CROSSTAR    e:HEV RS    X
駆動方式  FF  4WD    FF  4WD    FF  4WD           FF          FF  4WD
```

トヨタは「Z」「G」で、パワートレインは別の列見出しにある。ホンダは
`e:HEV X` と `X` のようにグレード名そのものが違う。

`gradeKey` は 名前/パワートレイン/駆動方式 の複合なので同定は成立するが、
`powertrain` に何を入れるかは決める必要がある（グレード名から切り出すか、
`e:HEV` / ガソリン という別の値を立てるか）。

## 発見6 型式が複数バリアントを覆う（既知の再確認）

```
6AA-GR3 … e:HEV X(FF) / e:HEV Z(FF) / e:HEV RS(FF)
6AA-GR4 … e:HEV X(4WD) / e:HEV Z(4WD)
```

2026-08-24 の調査どおり。型式の一意制約は既に外してあり、同定は複合キーで
行っているので、この点は対応済みである。

## 発見7 価格はJS描画（トヨタと同じ）

`https://www.honda.co.jp/Fit/webcatalog/type/list/` の生HTMLに7桁の金額は
1つも無い。トヨタと同じくブラウザで描画させて読む。

## 次にやること

1. `spec_sources` を車種につき複数登録する運用を決める（諸元用・装備用）
2. `e:HEV` を `powertrain` にどう写すかを決める
3. `〈〉` の意味を確かめる
4. ホンダの表記を `lib/feature-vocabulary.ts` の `others.ホンダ` に足す
   （このファイルに書いた、実際に読んだ表記だけ）
