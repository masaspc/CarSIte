# メーカー諸元表PDFの実地調査（2026-08-24）

トヨタ プリウスとスズキ アルトの諸元表PDFを**実際に取得して全ページ読んだ**記録。
設計書2章の調査を、パイロット（トヨタ1社）の外に1社広げたもの。

設計書はこう書いていた。

> **トヨタ1社のパイロット。** PDF取得 → LLM構造化 → 承認 → 公開までを数車種で貫き、
> **型式や括弧表記の罠を安く見つけてから**他社に広げる

その罠が見つかった。以下はすべてコマンドで確認した事実であり、推測は含まない。

## 調査対象

| | トヨタ プリウス | スズキ アルト |
|---|---|---|
| URL | `toyota.jp/pages/contents/prius/005_p_001/pdf/prius_spec_202607.pdf` | `suzuki.co.jp/car/alto/assets/pdf/detail.pdf` |
| サイズ | 455,398 バイト | 1,505,932 バイト |
| ページ数 | 6 | 2 |
| PDF版 | 1.6 | 1.3 |
| 暗号化 | **あり**（RC4 / R=4 / P=-3372、ユーザーパスワードは空） | **なし** |
| pdftotext | 字間が壊れて実用にならない | **そのまま読める** |

**PDFの性質はメーカーごとに大きく違う。** 暗号化の有無も、テキストが取れるかも共通ではない。
`pipeline/decrypt.ts` は暗号化されている場合だけ復号するので、どちらでも動く。

---

## 発見1【重大】型式はグレードの自然キーではない

設計書95行目はこう書いている。

> 国交省の型式指定で、**バリアントごとに一意**である。業界が実際に使う識別子であり、
> これを持てば同名グレード問題は構造的に解決する。

**スズキでは成立しない。**

`pdftotext -layout` で抽出した実際の表がこれである。

```
機種名        HYBRID X          HYBRID S              L        A
車名・型式      スズキ・5AA-ＨA97S              スズキ・3BA-HA37S
駆動方式      2WD  4WD      2WD  4WD        2WD  4WD    2WD  4WD
■機種記号     ABXB-3 ABXP-3  ABSB-3 ABSP-3   ABLE-3 ABLQ-3 ABAE-3 ABAQ-3
```

**型式は2つしかないのに、グレード×駆動方式は8つある。**
`5AA-HA97S` が HYBRID X の2WD/4WD と HYBRID S の2WD/4WD の4件を、
`3BA-HA37S` が L と A の4件を覆っている。

### 実際に起きること

`gradeKey()` は型式があればそれを返す。

```
グレード数: 8
gradeKey の種類: 2

スズキ・5AA-HA97S -> 4 件: HYBRID X/FF, HYBRID X/4WD, HYBRID S/FF, HYBRID S/4WD
スズキ・3BA-HA37S -> 4 件: L/FF, L/4WD, A/FF, A/4WD
```

DBに入れようとすると2件目で止まる。

```
制約: grades_type_designation_key | Key (type_designation)=(スズキ・5AA-HA97S) already exists.
```

`pipeline/apply.ts` の `applyNewGrade` が一意制約違反を捕まえて `stale` に倒すため
**クラッシュはしない**が、**8グレードのうち6件が永久に作られない**。
しかも承認キューには「一意制約に弾かれた」ではなく `stale` としか出ないため、
原因が分かりにくい。

### スズキが持っている一意な識別子

**機種記号**（`ABXB-3` / `ABXP-3` / `ABSB-3` / `ABSP-3` / `ABLE-3` / `ABLQ-3` / `ABAE-3` / `ABAQ-3`）
は8件とも異なる。これがスズキにおける実質的な自然キーである。

ただし `ExtractedGradeSchema`（`pipeline/extraction-schema.ts`）に機種記号を入れる欄が無い。
`typeDesignation` に機種記号を入れると意味が変わり、トヨタの型式と混ざる。

### 対処案

| 案 | 内容 | 懸念 |
|---|---|---|
| A | `grades_type_designation_key` の UNIQUE を外す | 型式が本当に一意なメーカー（トヨタ）での取り違え検知が効かなくなる |
| B | UNIQUE を `(model_id, type_designation, powertrain, drive_system)` に張り替える | 型式単独の一意性という前提を捨てることになる |
| C | `gradeKey()` を「型式 **＋** 複合キー」に変える（型式だけに倒さない） | 既存テスト `tests/unit/diff.test.ts` の期待値に触れる |
| D | 抽出スキーマに `variantCode`（機種記号）を足し、あれば最優先の自然キーにする | スキーマ変更とプロンプト変更が要る。メーカーごとの呼称差も吸収が要る |

**これは設計判断であり、実装者の一存で決めない。**
特にCは既存テストの期待値を変えることになるため、規約上そのまま進められない。

## 発見2【重大】車両本体価格は諸元表に載っていない

**トヨタもスズキも載っていない。**全ページ確認した。

トヨタの原本にはこう書かれている。

> 価格は販売店が独自に定めていますので、詳しくは各販売店にお尋ねください。

載っているのはオプション価格だけである（パノラミックビューモニター 60,500円、
デジタルキー 33,000円 など）。

スズキの車種ページ（`suzuki.co.jp/car/alto/detail/`）には
「メーカー希望小売価格（税込）」というラベルはあるが、**数値が画像**になっている。

詳細と対処案は設計書 7.4 に記載。

## 発見3 括弧記法の意味はメーカーごとに違う

設計書は括弧記法を「駆動方式のバリアント」として扱っている。トヨタではそうである。

| メーカー | 記法 | 意味 |
|---|---|---|
| トヨタ | `[ ]` | **E-Four**（駆動方式）。凡例 `●[ ]はE-Fourです。` |
| スズキ | `[ ]` | **アップグレードパッケージ装着車**（駆動方式ではない） |
| スズキ | `【 】` | **LEDヘッドランプ装着車**（駆動方式ではない） |

スズキは2種類の括弧を別の意味で同時に使う。
`ABSB-3【-H3】` は「機種記号 ABSB-3、LEDヘッドランプ装着車なら -H3」の意味であり、
`1,960［2,015］` は室内長がアップグレードパッケージで変わることを示す。

**「括弧の中身は E-Four」と決め打ちすると、スズキでは装備違いを駆動方式として取り込む。**
実際には各PDFの凡例を読んで意味を判定する必要がある。

## 発見4 同一PDF内で全角と半角が混在する

スズキの諸元表の**同じ行**で、型式の英字が全角と半角に分かれている。

```
スズキ・5AA-ＨA97S   ← Ｈ は U+FF28 FULLWIDTH LATIN CAPITAL LETTER H
スズキ・3BA-HA37S    ← H は U+0048 LATIN CAPITAL LETTER H
```

型式はキーとして使われ UNIQUE 制約もかかっているため、正規化しないと
同じ型式が別物として扱われうる。**現状コードベースに NFKC 正規化は一切ない**
（`grep -rn "NFKC\|normalize(" lib pipeline scripts db` の結果が空）。

`unicodedata.normalize('NFKC', ...)` を通せば両者とも `スズキ・5AA-HA97S` 形になる。
抽出結果を受け取る境界（`ExtractedSpecSchema` の parse 時）で正規化するのが素直である。

## 発見5【要確認】「テキストが取れない」という前提が再現しない

設計書2.2 と `pipeline/pdf.ts` のコメントはこう書いている。

> この諸元表は**字間が壊れた形でしかテキストが取れず**（「プラグイ ンハイブ リ ッ ド車」）、
> 正規表現でのパースは成立しない。表の読み取りはLLMの仕事である（設計書2.3）。

**再現しなかった。** 同じPDFに対し、poppler の `pdftotext -layout` でも、
プロジェクトが既に依存している `unpdf`（PDF.js）でも、壊れずに取れる。

```
トヨタ プリウス 主要諸元表
2.0L プラグインハイブリッド車 2.0L ハイブリッド車 1.8L ハイブリッド車
2WD 2WD/E-Four 2WD/E-Four
Z G Z G U
車両型式 2WD（前輪駆動方式） 6LA-MXWH61-AHXHB 6LA-MXWH61-AHXGB 6AA-MXWH60-AHXHB ...
E-Four（電気式4輪駆動方式） − − 6AA-MXWH65-AHXHB 6AA-MXWH65-AHXGB 6AA-ZVW65-AHXKB
車両重量 kg 1,570※1※2※3 1,560※1 1,420［1,480］※1※3 1,400［1,460］※1 1,360［1,420］
```

`プラグインハイブリッド車` は連結して取れている。型式も重量も括弧記法も原文のまま出る。

これが正しいなら、**LLMに6ページぶんの画像を渡す必要が無い場面がある**。
設計書6.4 の入力トークン概算「6ページ × (1,500〜3,000 + 画像分) ≒ 20,000〜30,000」は
画像を前提にしており、テキストだけ渡せば入力コストは大きく下がる。

ただし**装備表（2〜4ページ目）は別である。** あちらは
「緑＝標準装備／橙＝メーカーオプション／青＝販売店装着オプション」の**色**で
情報を表しており、テキスト抽出では色が落ちる。装備の判定には画像が要る。

したがって次のように分けられる可能性がある。

| 対象 | 必要なもの |
|---|---|
| 主要諸元表（型式・寸法・重量・燃費・エンジン） | **テキストで足りる** |
| 主要装備一覧表（20項目の standard/option/none） | 色の判定が要る＝画像 |

**元の記述がどの条件で得られたものかが分からないため、設計を変える判断は人間に委ねる。**
抽出器の設定違いか、別のページか、PDFの版が違ったのか。
少なくとも現行の `tests/fixtures/prius_spec_202607.pdf` では壊れない。
この事実は `tests/unit/golden-pdf.test.ts` の
「原本のテキストが壊れていない」で固定した。

## この調査の意味

設計書が「型式や括弧表記の罠を安く見つけてから他社に広げる」と書いたとおりになった。
**トヨタ1社だけを見ていたら、4つとも見つからなかった。**

発見1と2は設計の前提そのものに関わるため、人間の判断を待つ。
発見3と4は実装で吸収できるが、どちらも「1社を見て決めた規則が他社で破れる」という
同じ形をしている。パイロットを他社に広げる前に、もう1〜2社の諸元表を同じ手順で
読んでおくのが安全である。

## 再現手順

```bash
# トヨタ（暗号化あり）
curl -sL -o /tmp/prius.pdf https://toyota.jp/pages/contents/prius/005_p_001/pdf/prius_spec_202607.pdf
qpdf --show-encryption /tmp/prius.pdf

# スズキ（暗号化なし・テキスト抽出可）
curl -sL -o /tmp/alto.pdf https://www.suzuki.co.jp/car/alto/assets/pdf/detail.pdf
pdftotext -layout -f 2 -l 2 /tmp/alto.pdf - | head -12
```
