# 収集パイプライン 設計書

- **作成日**: 2026-08-14
- **対象**: サブプロジェクト2「収集パイプライン」
- **ステータス**: 承認済み（実装計画待ち）
- **前提**: サブプロジェクト1「データ基盤」完了（マージ済み、35コミット）

## 1. このサブプロジェクトが解く問題

サブプロジェクト1が終わった時点で、サイトは動くが**中身が無い**。

- DBには models=100 / grades=103 が入っているが、**59%が機械生成の架空データ**である
- 全103グレードが `draft` のため、公開ページは0件を表示する。これは正しい状態である
- 「本物のデータはサブプロジェクト2のクロールで投入する」と設計書に明記して先送りした

本サブプロジェクトは、その本物のデータを継続的に取得する仕組みを作る。

サブプロジェクト1の設計書が明示的に本サブプロジェクトへ送った宿題は次のとおり。

| 送られた宿題 | 本書での扱い |
|---|---|
| グレードの識別単位（世代・年次改良・パワートレイン違い） | 5章で確定。実データが答えを出した |
| 承認履歴・版管理・ロールバック | 5章・7章 |
| JSONB内部キーの命名規約・feature catalog | 6章 |
| EVの電費を `wltc_mode` と共用するか | 11章（未決として残す） |

## 2. 実地調査の結果

設計に入る前に、実際のメーカーサイトを調べた。**この調査結果が設計の前提を2度変えた**ため、経緯ごと記録する。

### 2.1 robots.txt は障害にならない

| メーカー | robots.txt | 諸元まわりの禁止 |
|---|---|---|
| トヨタ / レクサス | あり | `/cgi-bin/` `/data/` `/recall-notice/` `/detail/` のみ |
| ホンダ | あり | `/ridersvoice/` のみ |
| スバル | あり | 取説PDFの一部のみ（SEMrushBot は全面禁止） |
| ダイハツ | あり | `/media/` のみ |
| マツダ / 日産 / 三菱 | **404（存在しない）** | 宣言なし |
| スズキ | 302 リダイレクト | — |

諸元ページを禁止しているメーカーは1社もなかった。非商用・個人運営という位置づけと合わせ、**robots.txt を尊重する限り技術的にも規約的にも障害はない**と判断する。

### 2.2 HTMLスクレイピングは成立しない

当初の計画は「HTMLをクロールしてLLMで構造化」だったが、これは成立しない。

```
https://toyota.jp/prius/spec/index.html
  → 7,049 bytes、本文テキストは「prev next」のみ
  → 諸元語（全長・車両重量・WLTC）の出現 0件、<table> 要素 0件
```

価格とグレード名は素のHTMLに含まれるが、**諸元表はJavaScript描画**である。HTTPクロールでは取得できない。

### 2.3 権威ある情報源はPDFだった

実ブラウザで描画後のDOMを調べたところ、次のリンクが見つかった。

```
主要諸元表・装備一覧（PDF）を見る
  → https://toyota.jp/pages/contents/prius/005_p_001/pdf/prius_spec_202607.pdf
     455KB / 6ページ / テキスト層あり / robots.txt の許可範囲内
                                  ^^^^^^ ファイル名に年月
```

これはHTMLスクレイピングより**優れた入力**である。理由は3つ。

1. **権威性** — メーカーが「主要諸元表」として公開する正式文書そのもの。HTMLの断片を繋ぎ合わせるより信頼できる
2. **変更検知が自明** — ファイル名の年月と内容ハッシュで更新の有無が判定できる。変わっていないPDFにLLMを通す必要がない
3. **装備一覧が同梱** — サブプロジェクト3の「装備×価格の最適グレード探し」に必要な3値が、まさにこの文書に載っている

なお `pypdf` での素朴なテキスト抽出は、字間が壊れた形（`プラグイ ンハイブ リ ッ ド車`）でしか取れない。**正規表現によるパースは非現実的であり、ここがLLMを使うべき本当の場所**である。HTMLの整形ではなく、PDFの表構造の読み取りに使う。

### 2.4 グレードの一意制約は間違っていた

先送りにした最大の宿題に、実データが答えを出した。プリウスの諸元表の列構成はこうである。

```
        2.0L プラグインハイブリッド車 │ 2.0L ハイブリッド車 │ 1.8L ハイブリッド車
        2WD                          │ 2WD/E-Four         │ 2WD/E-Four
        Z      G                     │ Z      G           │ U
        ^^^^^^^^                       ^^^^^^^^
        同じ「Z」「G」が別パワートレインで重複
```

現行スキーマの `unique(model_id, name)` は、**プリウス1車種だけで違反する**。実際の識別単位は「車種 × パワートレイン × 駆動方式 × グレード名」だった。

さらに強い自然キーも見つかった。

```
車両型式  6LA-MXWH61-AHXHB / 6AA-MXWH60-AHXGB / 6AA-ZVW60-AHXKB
```

国交省の型式指定で、バリアントごとに一意である。業界が実際に使う識別子であり、これを持てば同名グレード問題は構造的に解決する。

また `車両重量 1,420 ［1,480］` という記法は「2WDの値［E-Fourの値］」を意味する。1列が2つの駆動方式を兼ねており、素朴なパーサは確実に取り違える。

### 2.5 装備の3値化は正しかった

PDF6ページ目の凡例。

```
標準設定 / 設定あり（ご注文時にご指定ください）/ メーカーオプション（ご注文時に申し受けます）
```

サブプロジェクト1で `feature_availability` を `standard / option / none / unknown` の4値にした判断は、**実際の公開文書の構造と一致していた**。boolean のままなら、ここで作り直しになっていた。

## 3. スコープ

### 対象

- **トヨタ1社のパイロット。** PDF取得 → LLM構造化 → 承認 → 公開までを数車種で貫き、型式や括弧表記の罠を安く見つけてから他社に広げる
- 諸元表PDFを情報源とする収集
- 変更検知、承認キュー、公開までの一連の流れ
- グレード識別単位のスキーマ修正（全メーカー共通の基盤なのでパイロットに含める）

### スコープ外

- トヨタ以外のメーカー（パイロットの知見を得てから別サブプロジェクトで拡張）
- ヘッドレスブラウザによるサイトマップ巡回（URLは手動登録する。11章参照）
- 差分ハイライト比較、装備×価格の最適グレード探し（サブプロジェクト3）
- TCO試算（サブプロジェクト4）
- 中古車相場（設計時に対象外と決定済み）

## 4. アーキテクチャ

```
① 登録   車種ごとに諸元ページURLを手で登録（一度きり）
         パイロットではトヨタの数車種。全メーカーに広げると約150件になる
   ↓
② 検出   週1回の定期実行。登録URLを描画してPDFリンクを取得
         ファイル名の年月 ＋ 内容のsha256 で変更判定
   ↓        変更なし → ここで終了（LLMを通さない）
③ 抽出   変更のあったPDFだけを Claude に投入 → 構造化JSON
   ↓
④ 承認   差分を承認キューへ。新規車種＝人間、価格改定＝自動
   ↓
⑤ 公開   承認されたものだけ published へ
```

**②の変更検知が費用対効果の要である。** メーカーは諸元表を年に数回しか更新しない。ハッシュが一致すればLLMを起動しないため、定常状態のコストはほぼゼロになる。初回のみ全件を処理する。

実行環境は GitHub Actions（cron、週1回）とする。諸元表の更新は年に数回であり、
週1回で十分に追随できる。ハッシュ一致で早期終了するため、空振りの回はほぼ無料である。Vercel の Functions には実行時間の上限があり、数十件のPDF取得とLLM呼び出しには向かない。DBへは Neon 経由で書き込む。

## 5. スキーマ変更

### 5.1 grades — 識別単位の修正

2.4の発見により、サブプロジェクト1が張った一意制約を変更する。**実データが「変えないと成立しない」と示している以上、避けられない。**

```
追加カラム:
  type_designation  text   -- 車両型式（例 6LA-MXWH61-AHXHB）。null 可
  powertrain        text   -- 例「2.0L プラグインハイブリッド車」。null 可

制約の張り替え:
  - unique(model_id, name)
  + unique(model_id, powertrain, drive_system, name)
  + unique(type_designation) where type_designation is not null
```

`type_designation` があるものはそれが真の自然キーである。無い場合（型式が公開されていない旧モデル等）は複合キーで識別する。

`powertrain` は既存の `engine_type`（`ガソリン` / `ハイブリッド` / `EV` / `ディーゼル` / `PHEV` の enum）とは別物である。
`engine_type` は検索用に正規化した分類、`powertrain` は諸元表の列見出しの原文（例「2.0L プラグインハイブリッド車」）であり、
同一 `engine_type` の中で排気量違いを区別するために必要になる。transmission を原文と分類に分けたのと同じ理屈である。

既存103件のフィクスチャは `powertrain` と `type_designation` が null になる。フィクスチャは非公開のままなので実害はない。

### 5.2 新規テーブル

| テーブル | 役割 | 主なカラム |
|---|---|---|
| `spec_sources` | 車種ごとの諸元ページURL（手動登録） | `model_id`, `page_url`, `registered_at`, `last_checked_at`, `consecutive_failures` |
| `spec_documents` | 取得したPDF | `spec_source_id`, `pdf_url`, `document_month`, `sha256`, `byte_size`, `fetched_at` |
| `extractions` | LLM抽出の生結果 | `spec_document_id`, `model_id_used`, `raw_output` (jsonb), `input_tokens`, `output_tokens`, `succeeded`, `error`, `extracted_at` |
| `change_requests` | 承認キュー | `spec_document_id`, `kind`, `diff` (jsonb), `status`, `decided_by`, `decided_at` |

**`extractions` に生の抽出結果をそのまま残すことが重要である。** スキーマを後から変えても再抽出せずに作り直せる。PDFのLLM処理が唯一の実コストなので、二度払わない設計にする。

`change_requests.kind` は `new_model` / `new_grade` / `price_change` / `spec_change` / `discontinued` を取る。7章の自動承認ルールがこの値で分岐する。

### 5.3 承認履歴

サブプロジェクト1が先送りした「承認履歴・版管理・ロールバック」は、`change_requests` と `extractions` の組で満たす。

- **誰が・いつ承認したか** → `change_requests.decided_by` / `decided_at`
- **何を承認したか** → `change_requests.diff`（適用前後の値）
- **ロールバック** → `diff` を逆適用する。生データは `extractions` に残っているため再構築も可能

## 6. LLMによる構造化

### 6.1 入力形式

**PDFを直接投入する。** Claude API はPDFをネイティブに受け取れる（ベータヘッダ不要、リクエスト32MB・600ページまで）。プリウスの諸元表は455KB・6ページで十分な余裕がある。

pypdf 等でテキスト抽出してから渡す方式は採らない。2.3で確認したとおり抽出テキストは字間が壊れており、表の列構造も失われるためである。PDFのまま渡し、モデルにページを見せる。

### 6.2 出力の強制

**Structured Outputs（`output_config.format`）でスキーマを強制する。** サブプロジェクト1で作った Zod スキーマをそのまま渡すことで、検証ルールの二重管理を避ける。

ただし Structured Outputs は Citations と併用できない（400になる）。出典ページ番号を持てないため、**どのページから取ったかの記録は諦め、代わりに `extractions.raw_output` に全文を残す**ことで追跡可能性を確保する。

### 6.3 モデル選択

`claude-opus-5` を使う。理由は次の2つ。

- 字間が壊れた日本語PDFから、括弧記法（`1,420 ［1,480］` = 2WD［E-Four］）の**意味**まで読み取る必要がある
- パワートレイン列とグレード行の対応という、表の2次元構造の解釈が必要である

ここを削ると誤抽出が増え、承認作業（人間の時間）が増える。トークン単価より人間の確認コストの方が高い。

### 6.4 コストの扱い

**本設計時点でコストは実測していない。** 設計環境に API 資格情報が無く、`count_tokens` を実行できなかった。

推定は出せるが、このプロジェクトでは「推測で設計を固めない」ことが繰り返し効いてきた（グレード識別、slug衝突、シード期待値はいずれも実測で判明した）。したがって実装計画に次の手順を含める。

1. 資格情報を設定した直後、プリウスのPDF1件を `count_tokens` で実測する
2. 1件の実測値から、パイロット範囲と全メーカー展開時（約150件）の両方を見積もる
3. 想定と桁が違えばモデル選択を見直してから本実行する

コスト削減の手段としては次を使う。

- **Batch API** — 50%引き。鮮度は「その日のうち」で足りるため、レイテンシと引き換えにできる
- **Files API** — PDFを一度アップロードして `file_id` で参照。再抽出時に再アップロードしない
- **プロンプトキャッシュ** — 指示とスキーマは全件共通なので前置きに置き、PDFを後ろに置く

## 7. 変更検知と承認モデル

### 7.1 変更検知

```
1. 登録済みURLを描画し、PDFリンクを取得する
2. ファイル名の年月（prius_spec_202607.pdf → 2026-07）を読む
3. 前回の spec_documents と比較
     年月が同じ かつ sha256 が同じ → 変更なし。終了
     いずれかが違う                → PDFを取得し sha256 を確認
4. sha256 が前回と異なる場合のみ、LLM抽出へ進む
```

ファイル名の年月だけに頼らないのは、年月を据え置いたまま内容を差し替える更新があり得るためである。**ハッシュが最終判定**であり、年月は取得前の足切りに使う。

### 7.2 承認の粒度

**車種単位（＝PDF1つ＝諸元表1つ）で一括承認する。** 諸元表がその単位で発行されるため、人間の確認単位としても自然である。グレード単位にすると初回だけで数千回の承認操作が発生し現実的でない。

### 7.3 2段構えの承認ルール

| 種別 | 承認 | 理由 |
|---|---|---|
| `new_model` | **人間** | 新しい車種のメタデータ全体が未検証 |
| `new_grade` | **人間** | 識別単位が正しく取れているかの確認が必要 |
| `price_change` | **自動** | 数値1つの変化で、誤りがあっても影響が限定的 |
| `spec_change` | **人間** | 諸元値の変更は誤抽出と区別がつかない |
| `discontinued` | **自動** | 消える方向の変更は誤情報を生まない |

自動承認された変更も `change_requests` に記録され、`decided_by` は `system` になる。後から追跡できる。

**サブプロジェクト1で導入した「車種の検証状態」との関係**: グレードを `published` にするには親車種が検証済みである必要がある。`new_model` の承認時に、車種の検証も同時に行う。

## 8. エラー処理

サブプロジェクト1で `DuplicateGradeError` と `assertEnum` に採用した思想を貫く。**壊れたデータを黙って通さず、どこが壊れているかを言って止まる。**

| 失敗 | 挙動 |
|---|---|
| PDF取得に失敗 | 指数バックオフで再試行。`consecutive_failures` が **3** に達したら「取得不能」として人間に上げる。**古いデータを使い続けたまま黙らない** |
| Zod検証に失敗 | `extractions` に生結果と `error` を残し、**部分的にも書き込まない**。人間の確認待ちにする |
| enumにない値 | エラーで停止し、どの車種のどの項目かを名指しする。enumを広げるかは人間が決める |
| PDFリンクが見つからない | サイト構造が変わった合図。「URL再登録が必要」として上げる。**推測でURLを組み立てない** |
| 型式が取れない | エラーにしない。`type_designation` を null にし、複合キーで識別する |

## 9. テスト

### ゴールデンファイル

`tests/fixtures/prius_spec_202607.pdf` を実物のまま置く。正解が判明しているため、回帰テストの基準になる。

```
期待される抽出結果（実物から確認済み）:
  2.0L PHEV (2WD)        → Z, G
  2.0L HV   (2WD/E-Four) → Z, G      ← 同じ Z, G が再登場
  1.8L HV   (2WD/E-Four) → U
  車両重量 1,420 ［1,480］ → 2WD=1420, E-Four=1480
  型式 6LA-MXWH61-AHXHB ほか
```

これが通れば、**同名グレード問題と括弧記法の両方**を同時に担保できる。

### ユニットテスト（DB非依存）

- ファイル名からの年月パース（`prius_spec_202607.pdf` → `2026-07`、不正形式の扱い）
- 変更判定（年月一致＋ハッシュ一致 → 変更なし、等の組み合わせ）
- 差分計算と `kind` の判定
- 自動承認ルール（`price_change` は自動、`spec_change` は人間）

### 統合テスト（実DB）

- 承認されていない `change_request` が公開に反映されないこと
- 未検証の車種配下のグレードが `published` にできないこと（サブプロジェクト1のゲートが効いていること）
- ロールバックで元の値に戻ること

### LLM抽出のテスト

ゴールデンPDFに対する抽出は、**実際にAPIを呼ぶテスト**とする。モックでは表構造の解釈という肝心な部分を検証できない。CIでは毎回走らせず、手動またはスケジュール実行にしてコストを抑える。

## 10. 完了条件

1. `npm run build` が ESLint 警告0で通り、ユニット・統合テストが通る
2. `spec_sources` にトヨタの数車種が登録され、URLから諸元表PDFを取得できる
3. 同じPDFに対して2回実行したとき、2回目はLLMを呼ばない（変更検知が効いている）
4. ゴールデンPDFの抽出結果が、9章の期待値と一致する（同名グレードが別レコードになり、括弧記法が2つの値に分解されている）
5. `change_requests` に差分が積まれ、管理画面から車種単位で承認できる
6. 承認したグレードだけが公開ページに現れる
7. 未承認のもの、および未検証の車種配下のものが公開されない
8. 抽出のトークン数とコストが `extractions` に記録され、実測値からパイロット範囲と
   全メーカー展開時（約150件）の両方の見積もりが出せる

## 11. リスクと未決事項

### 本サブプロジェクトで対応する

| 項目 | 内容 | 対応 |
|---|---|---|
| LLMの誤抽出 | 表構造の解釈を誤り、値が列をまたぐ | ゴールデンPDFで回帰テスト。承認を人間が通す |
| 初回のコスト | 全メーカー展開時は約150件を一度に処理する | Batch API と、実測に基づく事前見積もり。パイロットは数件なので影響は小さい |
| サイト構造の変更 | PDFリンクの位置が変わる | 見つからなければ「再登録が必要」として上げる。推測しない |

### 意図的に先送りする

| 項目 | 送り先 | 理由 |
|---|---|---|
