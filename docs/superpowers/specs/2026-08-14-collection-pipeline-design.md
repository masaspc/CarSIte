# 収集パイプライン 設計書

- **作成日**: 2026-08-14
- **対象**: サブプロジェクト2「収集パイプライン」
- **ステータス**: 承認済み（実装計画待ち）
- **前提**: サブプロジェクト1「データ基盤」完了（マージ済み、35コミット）

## 1. このサブプロジェクトが解く問題

サブプロジェクト1が終わった時点で、サイトは動くが**中身が無い**。

- DBには models=100 / grades=103 が入っているが、**59%が機械生成の架空データ**である
- 全103グレードが `draft` のため、公開ページは0件を表示する。これは正しい状態である
- 「本物のデータはサブプロジェクト2のクロールで投入する」と設計書に明記して先送りした

本サブプロジェクトは、その本物のデータを継続的に取得する仕組みを作る。

サブプロジェクト1の設計書が明示的に本サブプロジェクトへ送った宿題は次のとおり。

| 送られた宿題 | 本書での扱い |
|---|---|
| グレードの識別単位（世代・年次改良・パワートレイン違い） | 5章で確定。実データが答えを出した |
| 承認履歴・版管理・ロールバック | 5章・7章 |
| JSONB内部キーの命名規約・feature catalog | 6章 |
| EVの電費を `wltc_mode` と共用するか | 11章（未決として残す） |

## 2. 実地調査の結果

設計に入る前に、実際のメーカーサイトを調べた。**この調査結果が設計の前提を2度変えた**ため、経緯ごと記録する。

### 2.1 robots.txt は障害にならない

| メーカー | robots.txt | 諸元まわりの禁止 |
|---|---|---|
| トヨタ / レクサス | あり | `/cgi-bin/` `/data/` `/recall-notice/` `/detail/` のみ |
| ホンダ | あり | `/ridersvoice/` のみ |
| スバル | あり | 取説PDFの一部のみ（SEMrushBot は全面禁止） |
| ダイハツ | あり | `/media/` のみ |
| マツダ / 日産 / 三菱 | **404（存在しない）** | 宣言なし |
| スズキ | 302 リダイレクト | — |

諸元ページを禁止しているメーカーは1社もなかった。非商用・個人運営という位置づけと合わせ、**robots.txt を尊重する限り技術的にも規約的にも障害はない**と判断する。

### 2.2 HTMLスクレイピングは成立しない

当初の計画は「HTMLをクロールしてLLMで構造化」だったが、これは成立しない。

```
https://toyota.jp/prius/spec/index.html
  → 7,049 bytes、本文テキストは「prev next」のみ
  → 諸元語（全長・車両重量・WLTC）の出現 0件、<table> 要素 0件
```

価格とグレード名は素のHTMLに含まれるが、**諸元表はJavaScript描画**である。HTTPクロールでは取得できない。

### 2.3 権威ある情報源はPDFだった

実ブラウザで描画後のDOMを調べたところ、次のリンクが見つかった。

```
主要諸元表・装備一覧（PDF）を見る
  → https://toyota.jp/pages/contents/prius/005_p_001/pdf/prius_spec_202607.pdf
     455KB / 6ページ / テキスト層あり / robots.txt の許可範囲内
                                  ^^^^^^ ファイル名に年月
```

これはHTMLスクレイピングより**優れた入力**である。理由は3つ。

1. **権威性** — メーカーが「主要諸元表」として公開する正式文書そのもの。HTMLの断片を繋ぎ合わせるより信頼できる
2. **変更検知が自明** — ファイル名の年月と内容ハッシュで更新の有無が判定できる。変わっていないPDFにLLMを通す必要がない
3. **装備一覧が同梱** — サブプロジェクト3の「装備×価格の最適グレード探し」に必要な3値が、まさにこの文書に載っている

なお `pypdf` での素朴なテキスト抽出は、字間が壊れた形（`プラグイ ンハイブ リ ッ ド車`）でしか取れない。**正規表現によるパースは非現実的であり、ここがLLMを使うべき本当の場所**である。HTMLの整形ではなく、PDFの表構造の読み取りに使う。

### 2.4 グレードの一意制約は間違っていた

先送りにした最大の宿題に、実データが答えを出した。プリウスの諸元表の列構成はこうである。

```
        2.0L プラグインハイブリッド車 │ 2.0L ハイブリッド車 │ 1.8L ハイブリッド車
        2WD                          │ 2WD/E-Four         │ 2WD/E-Four
        Z      G                     │ Z      G           │ U
        ^^^^^^^^                       ^^^^^^^^
        同じ「Z」「G」が別パワートレインで重複
```

現行スキーマの `unique(model_id, name)` は、**プリウス1車種だけで違反する**。実際の識別単位は「車種 × パワートレイン × 駆動方式 × グレード名」だった。

さらに強い自然キーも見つかった。

```
車両型式  6LA-MXWH61-AHXHB / 6AA-MXWH60-AHXGB / 6AA-ZVW60-AHXKB
```

国交省の型式指定で、バリアントごとに一意である。業界が実際に使う識別子であり、これを持てば同名グレード問題は構造的に解決する。

> **【要確認】2026-08-24 追記: この前提はトヨタでしか成立しない。**
> スズキ アルトの諸元表を実際に読んだところ、型式は `5AA-HA97S` と `3BA-HA37S` の2つしかなく、
> グレード×駆動方式の8バリアントを覆っていた。`gradeKey()` は8件を2キーに潰し、
> `grades_type_designation_key` の UNIQUE 制約は2件目の INSERT を拒否する（どちらも再現確認済み）。
> スズキで一意なのは**機種記号**（`ABXB-3` など）だが、抽出スキーマにその欄が無い。
> 詳細と対処案4件は [メーカー諸元表PDFの実地調査](../../research/2026-08-24-manufacturer-pdf-survey.md) を参照。

また `車両重量 1,420 ［1,480］` という記法は「2WDの値［E-Fourの値］」を意味する。1列が2つの駆動方式を兼ねており、素朴なパーサは確実に取り違える。

> **【要確認】2026-08-24 追記: 括弧の意味もメーカーごとに違う。**
> スズキでは `[ ]` が「アップグレードパッケージ装着車」、`【 】` が「LEDヘッドランプ装着車」で、
> どちらも駆動方式ではない。「括弧の中身は E-Four」と決め打ちすると装備違いを駆動方式として取り込む。
> あわせて、同一PDFの同じ行で型式の英字が全角（U+FF28）と半角（U+0048）に分かれている例も見つかった。
> コードベースに NFKC 正規化は無い。同上の調査記録を参照。

### 2.5 装備の3値化は正しかった

PDF6ページ目の凡例。

```
標準設定 / 設定あり（ご注文時にご指定ください）/ メーカーオプション（ご注文時に申し受けます）
```

サブプロジェクト1で `feature_availability` を `standard / option / none / unknown` の4値にした判断は、**実際の公開文書の構造と一致していた**。boolean のままなら、ここで作り直しになっていた。

## 3. スコープ

### 対象

- **トヨタ1社のパイロット。** PDF取得 → LLM構造化 → 承認 → 公開までを数車種で貫き、型式や括弧表記の罠を安く見つけてから他社に広げる
- 諸元表PDFを情報源とする収集
- 変更検知、承認キュー、公開までの一連の流れ
- グレード識別単位のスキーマ修正（全メーカー共通の基盤なのでパイロットに含める）
- **パイロットの対象からEV（bZ4X等）を外す。** 既存の `wltc_mode` は km/L を入れる想定で、
  EVの電費（Wh/km）とは単位が違う。同じ列に混ぜると並び替えと絞り込みが壊れる（11章参照）。
  EVを外せば、単位の判断を先送りしたまま安全にパイロットを回せる

### スコープ外

- トヨタ以外のメーカー（パイロットの知見を得てから別サブプロジェクトで拡張）
- ヘッドレスブラウザ全般（不要になった。4章・7.1参照）。新車種の発見も手動登録に任せる
- 差分ハイライト比較、装備×価格の最適グレード探し（サブプロジェクト3）
- TCO試算（サブプロジェクト4）
- 中古車相場（設計時に対象外と決定済み）

## 4. アーキテクチャ

```
① 登録   車種ごとにPDFのベースパスを手で登録（一度きり）
         例: /pages/contents/prius/005_p_001/pdf/prius_spec_
         パイロットではトヨタの数車種。全メーカーに広げると約150件になる
   ↓
② 検出   週1回の定期実行。ベースパス + 年月 + .pdf をHEADで探索して最新版を特定
         PDFを取得し、内容の sha256 で変更判定（7.1）
   ↓        変更なし → ここで終了（LLMを通さない）
③ 抽出   変更のあったPDFだけを Claude に投入 → 構造化JSON
   ↓
④ 承認   差分を承認キューへ。新規車種＝人間、価格改定＝自動
   ↓
⑤ 公開   承認されたものだけ published へ
```

**②の変更検知が費用対効果の要である。** メーカーは諸元表を年に数回しか更新しない。ハッシュが一致すればLLMを起動しないため、定常状態のコストはほぼゼロになる。初回のみ全件を処理する。

**ヘッドレスブラウザは使わない。** 諸元ページのHTMLは中身が空の器で、PDFリンクはJavaScriptが
描画してからでないと現れない（2.2）。当初はページを描画してリンクを拾う想定だったが、
実際に調べたところ**PDFのURLは年月を振れば直接見つけられる**ことが分かった（7.1）。
ブラウザを起動する必要がなくなり、CI側のブラウザ導入も消える。

実行環境は GitHub Actions（cron、週1回）とする。諸元表の更新は年に数回であり、
週1回で十分に追随できる。ハッシュ一致で早期終了するため、空振りの回はほぼ無料である。Vercel の Functions には実行時間の上限があり、数十件のPDF取得とLLM呼び出しには向かない。DBへは Neon 経由で書き込む。

## 5. スキーマ変更

### 5.1 grades — 識別単位の修正

2.4の発見により、サブプロジェクト1が張った一意制約を変更する。**実データが「変えないと成立しない」と示している以上、避けられない。**

```
追加カラム:
  type_designation  text          -- 車両型式（例 6LA-MXWH61-AHXHB）。null 可
  powertrain        text NOT NULL DEFAULT ''   -- 例「2.0L プラグインハイブリッド車」

制約の張り替え:
  - unique(model_id, name)
  + unique(model_id, powertrain, drive_system, name)
    unique(model_id, slug)         -- 残す。ただし slug の生成規則を変える（下記）
  + unique(type_designation) where type_designation is not null
```

**`powertrain` を NOT NULL DEFAULT '' にすることが必須である。** nullable にしてはならない。
PostgreSQL の UNIQUE 制約は既定で NULL 同士を「異なる値」として扱うため、`powertrain` が null の行は
一意制約をすり抜けて何行でも入る。本プロジェクトの Neon（PostgreSQL 18.4）で実測して確認した。

```sql
create table _probe (a int, b text, unique(a,b));
insert into _probe values (1, null);
insert into _probe values (1, null);   -- 通る。2行入る
```

つまり nullable のままでは、同名グレードを弾くという制約の目的をまったく果たさない。
値が取れない場合は空文字を入れる。`drive_system` は既に NOT NULL なので、
複合キーの3列すべてが NOT NULL になり、一意性が保証される。

一方 `unique(type_designation)` は **nullable のままでよい**。型式が公開されていない車種が
複数あっても互いに衝突しないことが、ここでは望ましい挙動だからである。同じ NULL 挙動が、
一方では欠陥になり他方では要件になる。

**`unique(model_id, slug)` も同じ問題を持つ。** `slug` は公開URLの識別子であり、
`/toyota/prius/z` のような経路を作る。プリウスの「Z」が2つある以上、
現在の生成規則（グレード名のみから作る）では衝突する。制約は残したまま、
**slug の生成規則にパワートレインと駆動方式を織り込む**。

```
現在: Z                    → z            （2つの Z が衝突する）
変更: Z / 2.0L PHEV / 2WD  → z-phev-2wd
      Z / 2.0L HV   / 2WD  → z-hv-2wd
```

サブプロジェクト1で決めた「slug は一度発行したら変えない」規則は維持する。
既存103件の slug は変更しない。新規に取り込む行から新しい規則を適用する。

既存103件のフィクスチャは `powertrain` が空文字、`type_designation` が null になる。
既存データは1車種につき同名グレードを持たないため、新しい複合制約でも衝突しない
（`unique(model_id, name)` を満たしていたものは `unique(model_id, '', drive_system, name)` も満たす）。
マイグレーションは既存行を壊さない。この点は実装計画で実際にマイグレーションを流して確認する。

### 5.2 新規テーブル

| テーブル | 役割 | 主なカラム |
|---|---|---|
| `spec_sources` | 車種ごとのPDFベースパス（手動登録） | `model_id`, `pdf_base_url`, `known_month`, `registered_at`, `last_checked_at`, `consecutive_failures` |
| `spec_documents` | 取得したPDF | `spec_source_id`, `pdf_url`, `document_month`, `sha256`, `byte_size`, `page_count`, `stored_path`, `fetched_at` |
| `extractions` | LLM抽出の生結果 | `spec_document_id`, `model_id_used`, `raw_output` (jsonb), `input_tokens`, `output_tokens`, `succeeded`, `error`, `extracted_at` |
| `change_requests` | 承認キュー | `spec_document_id`, `kind`, `target_key`, `diff` (jsonb), `status`, `decided_by`, `decided_at`, `applied_at` |

**`extractions` に生の抽出結果をそのまま残す。** スキーマを後から変えても、多くの場合は再抽出せずに作り直せる。

ただしこれだけでは不十分である。Structured Outputs は**スキーマで要求した項目しか返さない**ため、
後から新しい項目（例: 最小回転半径）を追加したくなったとき、`raw_output` には元々入っていない。
したがって **PDF そのものを保存する**（`spec_documents.stored_path`）。メーカーのURLは改定のたびに
差し替わるため、後から取り直せる保証がない。455KB × 150件 ≒ 70MB で、保存コストは無視できる。

- 既存項目の作り直し → `raw_output` から。無料
- 新項目の追加 → 保存したPDFから再抽出。LLM費用がかかるが、可能である

**`change_requests.target_key`** は適用対象を一意に指す文字列（グレードなら型式または複合キー）。
`unique(spec_document_id, kind, target_key)` を張ることで、cronの重複起動や再実行で
同じ変更が二重に積まれることを防ぐ。

`change_requests.kind` は `new_model` / `new_grade` / `price_change` / `spec_change` / `discontinued` を取る。7章の自動承認ルールがこの値で分岐する。

### 5.3 承認履歴

サブプロジェクト1が先送りした「承認履歴・版管理・ロールバック」は、`change_requests` と `extractions` の組で満たす。

- **誰が・いつ承認したか** → `change_requests.decided_by` / `decided_at`
- **何を承認したか** → `change_requests.diff`（適用前後の値）
- **ロールバック** → `diff` を逆適用する。生データは `extractions` に残っているため再構築も可能

### 5.4 トランザクションが無い前提での冪等性

**`@neondatabase/serverless` の HTTP ドライバはトランザクションを持たない。**
サブプロジェクト1で確認済みの制約であり、`npm run db:seed -- --force` が不可逆なのも同じ理由である。
複数の書き込みをまとめて巻き戻す手段が無いため、冪等性で守る。

| 危険 | 対策 |
|---|---|
| cronの重複起動で同じ変更が二重に積まれる | `unique(spec_document_id, kind, target_key)` |
| 承認ボタンの二度押しで二重適用 | `update change_requests set status='applied' where id=$1 and status='pending'` の更新行数が0なら何もしない |
| 古い画面から、既に別の変更が当たった行を承認 | `change_requests` に適用時点の期待値を持ち、現在値と食い違えば適用せず `stale` にして人間に戻す |
| 適用の途中で落ちる | 1つの `change_request` の適用は単一行の UPDATE に収める。跨ぐ場合は再実行で同じ結果になる形に分割する |

## 6. 構造化

### 6.0 【2026-08-29 改訂】LLMをパイプラインから外した

**この章は当初「LLMによる構造化」だった。実装と実地調査を経て、運用モデルを変えた。**

きっかけは6.1の前提が崩れたことである。「抽出テキストは字間が壊れており、表の列構造も
失われる」と書いていたが、**再現しなかった**。poppler の `pdftotext -layout` でも、
プロジェクトが既に依存している `unpdf`（PDF.js）でも、プリウスの諸元表は壊れずに取れる。

```
2.0L プラグインハイブリッド車 2.0L ハイブリッド車 1.8L ハイブリッド車
車両型式 2WD（前輪駆動方式） 6LA-MXWH61-AHXHB 6LA-MXWH61-AHXGB ...
車両重量 kg 1,570※1※2※3 1,560※1 1,420［1,480］※1※3 1,400［1,460］※1
```

型式8件も括弧記法も正規表現で取れることを確認した。**主要諸元表の読み取りに
LLMは要らない。**

一方で**装備一覧表にはLLMが要る**。あちらは
「緑＝標準装備／橙＝メーカーオプション／青＝販売店装着オプション」という**色**で
情報を表しており、テキスト抽出では色が落ちる。

そこで役割を分けた。

| | 誰が | 何を | APIキー |
|---|---|---|---|
| **無人**（週1回） | GitHub Actions | PDFが変わったかを sha256 で検知し、原本を保存する | 不要 |
| **有人**（変更時） | 対話セッションの Claude | PDFを読んで諸元を起こし、承認キューに積む | 不要 |
| **先送り** | 未定 | 全車種の装備確認 | 要る見込み |

**装備の取り込みはこのサブプロジェクトの範囲から外す。** サイトを作る段階で、
必要な車種について改めて行う。

> **2026-08-30 追記 —— 上の「要る見込み」は誤りだった。**
> 装備の判定にAPIキーは要らない。対話セッションの Claude 自身がPDFを画像として
> 読めるためである。`pdftoppm` で300dpiのPNGに書き出し、凡例のスウォッチのRGBを
> 基準にセル背景色を判定すれば、緑・橙・青・白を区別できる。プリウス8グレード
> ×20項目をこの方法で取り込んだ（手順は `docs/operations/collect.md` の
> 「装備の読み取り方」）。
>
> 「LLMが要る」までは正しく、「APIキーが要る」が誤り。無人の週次ジョブに
> 組み込むならAPIキーは要るが、有人の取り込みなら要らない。この区別を
> 見落としていた。

### 6.0.1 週次ジョブは「見張り」になる

`scripts/collect.ts` は次で止まる。

```
年月探索 → 取得 → 事前検査 → 復号 → sha256 照合
  ├ 前回と同じ → last_checked_at だけ更新
  └ 変わった  → spec_documents に記録し、原本を storage/ に保存
```

`change_requests` は作らない。「どの車種の諸元表がいつ変わったか」という事実だけが
自動で残り、人間（と対話セッションの Claude）がそれを見て取り込みに行く。

### 6.0.2 取り込みの経路

既存の安全機構（差分・承認・冪等な適用・stale検知）は**すべてそのまま通す**。
変わるのは `ExtractedSpec` の生産者だけである。

```
PDFを読む
  → tests/fixtures/<model-slug>-<month>.spec.json（ExtractedSpec 形）
  → npm run ingest-spec -- --model-slug <slug>
      → normalizeGrades → computeChanges → change_requests
  → /admin/changes で承認 → applyChangeRequest
```

JSONはリポジトリにコミットする。何をどう読んだかが差分で追え、テストからも検証できる。
`extractions` には `modelIdUsed: 'manual'` で記録を残し、監査証跡の形を揃える。

### 6.0.3 装備と価格は比較対象から外す

`computeChanges` に比較オプションを足す（既定は現状のまま）。

```ts
computeChanges(existing, incoming, { comparePrice: false, compareFeatures: false })
```

**どちらも諸元表に載っていないため**である（価格については7.4を参照）。
無いものを null として比較すると、毎回・全グレードに空振りの `price_change` と
装備の `spec_change` が立つ。実測で確認した。

### 6.0.4 LLM抽出のコードは残す

`pipeline/extract.ts` と `pipeline/extraction-schema.ts` は削除しない。
`collect.ts` からの呼び出しを外すだけにする。装備確認を行う段階で、
プロンプトと Structured Outputs の定義がそのまま使える。

以下 6.1〜6.4 は、その装備確認を行う際に有効な記述として残す。
**ただし 6.1 の「抽出テキストは字間が壊れる」という記述は誤りである**（上記）。

### 6.1 入力形式

**PDFを直接投入する。** Claude API はPDFをネイティブに受け取れる（ベータヘッダ不要）。上限は
リクエスト全体で **32MB**、**600ページ**。ただし600ページはコンテキストウィンドウが1M以上の場合で、
1M未満なら100ページになる。`claude-opus-5` は既定で1Mコンテキストなので600ページが適用される。
プリウスの諸元表は455KB・6ページで、どちらの上限にも十分な余裕がある。

**実物の諸元表は暗号化されている。** 編集制限のためで、ユーザーパスワードは空なので読むことはできる
（トレーラに `/Encrypt` がある）。一方 Claude API のPDF要件には「パスワード/暗号化なしの標準PDF」と
書かれているため、そのまま受け付けられるかは**実呼び出しで確かめるまで分からない**。
実装計画のTask 16（最初の実呼び出し）で必ず確認し、拒否されるなら収集の前段に
復号の工程（`qpdf --decrypt` など）を足す。

この暗号化は、ページ数を数えるライブラリの選択にも影響した。`pdf-lib` は
`ignoreEncryption` を付けても本文を復号しないため、このPDFのページツリーを解決できない。
PDF.js（`unpdf`）を使う。

取得したPDFは外部から来るファイルなので、LLMに渡す前に検査する。

- Content-Type が `application/pdf` であること
- **10MB を超えたら拒否**（諸元表が10MBになることはない。異常の合図である）
- **50ページを超えたら拒否**（取説PDFを掴んでいる可能性が高い）
- ページ数が読めない、あるいはPDFとして開けないものは取得失敗として扱う

これは費用の暴発と、意図しない文書をモデルに読ませることの両方を防ぐ。

### 6.2 出力の強制

**Structured Outputs（`output_config.format`）でスキーマを強制する。** サブプロジェクト1で作った
Zod スキーマを JSON Schema に変換して渡す（Zodオブジェクトをそのまま渡すのではない）。
変換元が1つなので、検証ルールの二重管理を避けられる。

Structured Outputs は**スキーマで要求した項目しか返さない**。将来の項目追加に備えて
PDF本体を保存しておく必要があるのはこのためである（5.2参照）。

ただし Structured Outputs は Citations と併用できない（400になる）。出典ページ番号を持てないため、**どのページから取ったかの記録は諦め、代わりに `extractions.raw_output` に全文を残す**ことで追跡可能性を確保する。

### 6.3 モデル選択

`claude-opus-5` を使う。理由は次の2つ。

- 字間が壊れた日本語PDFから、括弧記法（`1,420 ［1,480］` = 2WD［E-Four］）の**意味**まで読み取る必要がある
- パワートレイン列とグレード行の対応という、表の2次元構造の解釈が必要である

ここを削ると誤抽出が増え、承認作業（人間の時間）が増える。トークン単価より人間の確認コストの方が高い。

### 6.4 コストの扱い

**本設計時点でトークン数は実測していない。** 設計環境に API 資格情報が無く、`count_tokens` を実行できなかった。

公式ドキュメントの数値からの概算は次のとおり。PDFは1ページあたり本文 1,500〜3,000 トークンに加え、
各ページが画像としても渡されるぶんの画像トークンがかかる。

```
入力  6ページ × (1,500〜3,000 + 画像分) ≒ 20,000〜30,000 トークン
        → $5/1M × 0.03M ≒ $0.15
出力  グレード数 × 項目数の構造化JSON ≒ 5,000〜10,000 トークン
        → $25/1M × 0.01M ≒ $0.25
合計  1車種あたり ≒ $0.4、Batch API で半額なら ≒ $0.2
      全メーカー展開時 150件 ≒ $30〜60（初回のみ）
```

この桁なら費用は制約にならない。ただしこれは概算である。このプロジェクトでは
「推測で設計を固めない」ことが繰り返し効いてきた（グレード識別、slug衝突、シード期待値は
いずれも実測で判明した）。したがって実装計画に次の手順を含める。

1. 資格情報を設定した直後、プリウスのPDF1件を `count_tokens` で実測する
2. 1件の実測値から、パイロット範囲と全メーカー展開時（約150件）の両方を見積もる
3. 想定と桁が違えばモデル選択を見直してから本実行する

コスト削減の手段としては次を使う。

- **Batch API** — 50%引き。鮮度は「その日のうち」で足りるため、レイテンシと引き換えにできる
- **Files API** — PDFを一度アップロードして `file_id` で参照。再抽出時に再アップロードしない。
  ベータヘッダ `files-api-2025-04-14` が必要。保存期間には限りがあるため、
  **`file_id` を恒久的な保管手段として当てにしない**。原本は自前で保存する（5.2の `stored_path`）
- **プロンプトキャッシュ** — 指示とスキーマは全件共通なので前置きに置き、PDFを後ろに置く

## 7. 変更検知と承認モデル

### 7.1 変更検知

```
登録済み: base = https://toyota.jp/pages/contents/prius/005_p_001/pdf/prius_spec_
          known = 2026-07（前回見つかった年月。初回は null）

1. 今月から known の翌月まで、新しい順に HEAD を投げる
     200 が返った最初の年月 → それが最新版。3へ
     全て404             → 2へ
2. known 自体を HEAD で確認
     200 → 更新なし。last_checked_at だけ更新して終了（本文も取らない）
     404 → ベースパスが死んでいる。「URL再登録が必要」として人間に上げる
3. PDF を GET し、6.1 の検査を通したうえで sha256 を計算する
4. 直近の spec_documents の sha256 と比較
     一致   → 変更なし。fetched_at だけ更新して終了（LLMを呼ばない）
     不一致 → 新しい spec_documents 行を作り、LLM抽出へ進む
```

**この方式が成立することは実測で確認した。**

```
prius_spec_202608.pdf → 404      prius_spec_202607.pdf → 200 (455,398 bytes)
prius_spec_202606.pdf → 404      prius_spec_202512.pdf → 404
```

同時に存在する年月は1つだけで、古い版は消える。だから「200が返った年月が最新版」と言い切れる。
定常状態のHTTPリクエストは1車種あたり週2〜3回で済む。

一方、パス中の `005_p_001` は車種ごとに違う。yaris / corolla / alphard で同じ形を試すと
すべて404だった。**この部分は推測できないので、人が一度登録する**（①）。設計の
「PDFのURLを推測で組み立てない」（8章）はここに効いている。組み立ててよいのは
登録済みベースパスの年月部分だけである。

**判定は必ず sha256 で行う。** 年月が同じでも内容が差し替わることがあるため、
年月は探索にだけ使い、変更の有無はハッシュで決める。PDFは1件455KB程度で、
150件を毎週取得しても週70MBにすぎない。**高いのはLLMであって取得ではない。**

**取りこぼしの唯一の経路と、その対策。** 新しい諸元表が別のセクションIDで公開され、
かつ古いPDFが残されたままだと、探索は古い版を見つけ続けて更新に気づかない。
これを検出するため、**見つかった年月が18か月以上前なら、内容が変わっていなくても
「要確認」として人間に上げる**。販売中の車種の諸元表が18か月変わらないのは、
更新が無いのではなく探索が外れている可能性のほうが高い。

### 7.2 承認の粒度

**車種単位（＝PDF1つ＝諸元表1つ）で一括承認する。** 諸元表がその単位で発行されるため、人間の確認単位としても自然である。グレード単位にすると初回だけで数千回の承認操作が発生し現実的でない。

### 7.3 2段構えの承認ルール

| 種別 | 承認 | 理由 |
|---|---|---|
| `new_model` | **人間** | 新しい車種のメタデータ全体が未検証 |
| `new_grade` | **人間** | 識別単位が正しく取れているかの確認が必要 |
| `spec_change` | **人間** | 諸元値の変更は誤抽出と区別がつかない |
| `discontinued` | **人間** | 下記のとおり、当初の「自動」から変更した |
| `price_change` | **条件付き自動** | 下記の範囲内なら自動、外れたら人間 |

**`price_change` の自動承認には歯止めを付ける。** 価格は公開ページの絞り込みと並び替えに
直接効く（`db/queries.ts`）ため、誤った値がそのまま検索結果を歪める。次の条件をすべて満たす場合のみ自動とする。

- 変化率が **±20%以内**
- 変化後の値が **50万円以上 3,000万円以下**
- 同じPDFから生成された `price_change` が、その車種のグレード数の半分を超えていない
  （全グレードが一斉に動くのは、価格改定ではなく列の取り違えを疑うべき状況である）

いずれかを外れたら人間の承認に回す。安全側に倒しても、外れるのは稀なので手間は増えない。

**`discontinued` は自動承認しない。当初の設計から変更した。**
「PDFにグレードが載っていない」ことの原因は2つあり、区別がつかない。

1. 本当に廃止された
2. 抽出が失敗した、あるいは諸元表の構成が変わって読み落とした

2を自動承認すると、**販売中のグレードを誤って非公開にする**。これは
「取得に失敗したとき古いデータを黙って使い続けない」という8章の原則の裏返しであり、
同じ理由で、消える方向の変更も黙って通してはいけない。廃止は人間が確認する。

自動承認された変更も `change_requests` に記録され、`decided_by` は `system` になる。後から追跡できる。

**サブプロジェクト1で導入した「車種の検証状態」との関係**: グレードを `published` にするには親車種が検証済みである必要がある。`new_model` の承認時に、車種の検証も同時に行う。

### 7.4 【要確認】諸元表に車両本体価格は載っていない

**2026-08-24 追記。実物のプリウス諸元表（2026-07版）を全6ページ読んで判明した。**
**2026-08-29 追記: 当面の措置として、6.0.3 のとおり価格を比較対象から外す。**
下記の対処案A〜Cのうち、Cを「当面の措置」として採る形になる。取得元を増やすか
（案B）、価格改定の検知を目的から外すか（案A）は未決のままである。

この文書に車両本体価格は無い。載っているのはオプション価格だけである
（パノラミックビューモニター 60,500円、デジタルキー 33,000円 など）。
原本にこう書かれている。

> 価格は販売店が独自に定めていますので、詳しくは各販売店にお尋ねください。

これは7.3 の前提を崩す。**自動承認されるのは `price_change` だけ**なのに、
その `price_change` の入力が諸元表から取れない。

実際に何が起きるかはコードで確認した。

1. 抽出は指示どおり `price: null` を返す（プロンプトが「表に書かれていない値は
   推測せず null に」と指示している）
2. `computeChanges` は「値 → null」を変更として立てる。これは
   `tests/unit/diff.test.ts` が意図的に固定している挙動であり、一般には正しい
   （諸元が本当に消えることはある）
3. 結果、**毎回・全グレードに `price_change` が積まれる**。
   `decideApproval` は「変更前後のどちらかの価格が数値として取れていません」で
   自動承認を拒むので誤った自動適用は起きないが、承認キューが空振りで埋まる
4. 人間が誤って承認すると `grades.price` の NOT NULL 制約に当たる。
   これは `pipeline/apply.ts` の `NON_NULLABLE_GRADE_COLUMNS` で
   `stale` に倒すよう修正済み（DBエラーでは落ちなくなった）

4は塞いだが、3は設計判断が要る。選択肢は次のとおり。

| 案 | 内容 | 懸念 |
|---|---|---|
| A | 諸元表由来の抽出では `price` を比較対象から外す | 価格改定を全く検知できなくなる。7.3 の自動承認が空文になる |
| B | 価格は別の取得元（価格表PDF・グレード比較ページ）から取る | 取得元が増える。パイロットの範囲を超える |
| C | `after` が null の `price_change` は最初から立てない | 「価格が消えた」を検知できなくなるが、諸元表にそもそも価格が無い以上は無害 |

**Cが最も軽いが、`computeChanges` の既存の挙動と既存テストに触れるため、
実装者の一存で決めない。** 価格改定の検知をこのパイプラインの目的に含めるのか、
含めるなら取得元をどうするのかは、人間が決める必要がある。

**2026-08-29 追記: 実データで確定した帰結。**

プリウスの諸元表8グレードを実際に取り込んだ結果、`new_grade` は適用できないことが
分かった。`grades.price` が NOT NULL であり、諸元表に価格が無いためである。
`pipeline/apply.ts` の `buildNewGradeValues` が価格の無い作成を拒む。

つまり**諸元表からの取り込みは既存グレードの諸元更新に限られる**。新規グレードの
作成には価格の取得元（案B）か、管理画面での人手入力が要る。
プリウスの8件は承認キューに `pending` のまま残してある。

## 8. エラー処理

サブプロジェクト1で `DuplicateGradeError` と `assertEnum` に採用した思想を貫く。**壊れたデータを黙って通さず、どこが壊れているかを言って止まる。**

| 失敗 | 挙動 |
|---|---|
| PDF取得に失敗 | 指数バックオフで再試行。`consecutive_failures` が **3** に達したら「取得不能」として人間に上げる。**古いデータを使い続けたまま黙らない** |
| Zod検証に失敗 | `extractions` に生結果と `error` を残し、**部分的にも書き込まない**。人間の確認待ちにする |
| enumにない値 | エラーで停止し、どの車種のどの項目かを名指しする。enumを広げるかは人間が決める |
| 探索が全て404 | ベースパスが死んでいる。「URL再登録が必要」として上げる。**ベースパス自体を推測しない** |
| 見つかった年月が18か月以上前 | 別のセクションIDに移った可能性。「要確認」として上げる（7.1） |
| 型式が取れない | エラーにしない。`type_designation` を null にし、複合キーで識別する |
| PDFが検査を通らない | 6.1 の上限（10MB / 50ページ / Content-Type）を外れたら取得失敗として扱い、LLMに渡さない |
| 承認の適用中に落ちた | `change_requests.status` を見て再実行する。適用は冪等なので二重には当たらない（5.4） |
| 適用しようとした行が既に変わっていた | 適用せず `stale` にして人間に戻す。上書きしない |

9. 承認したグレードだけが公開ページに現れる
10. 未承認のもの、および未検証の車種配下のものが公開されない
11. ~~抽出のトークン数とコストが `extractions` に記録され、実測値からパイロット範囲と
    全メーカー展開時（約150件）の両方の見積もりが出せる~~

**【2026-08-29 改訂】** 6.0 でLLMをパイプラインから外したため、条件5と11を差し替える。

5'. 諸元表から起こした正解データに対し、同名グレードが別レコードになり、
    括弧記法が2つの値に分解され、複合キーが全件で異なることを検証してある
    （`tests/unit/golden-pdf.test.ts`。APIキー不要）

11'. **週次ジョブがAPIキー無しで完結する。** PDFの変更を sha256 で検知して
    `spec_documents` に記録し、原本を保存するところまでを無人で行う。
    取り込みは `npm run ingest-spec` を通じて有人で行い、既存の承認・適用フローに乗る

トークン数とコストの実測は、装備確認を行う段階の課題として持ち越す。
その時点で初めて `ANTHROPIC_API_KEY` が要る。

## 11. リスクと未決事項

### 本サブプロジェクトで対応する

| 項目 | 内容 | 対応 |
|---|---|---|
| LLMの誤抽出 | 表構造の解釈を誤り、値が列をまたぐ | ゴールデンPDFで回帰テスト。承認を人間が通す |
| 初回のコスト | 全メーカー展開時は約150件を一度に処理する | Batch API と、実測に基づく事前見積もり。パイロットは数件なので影響は小さい |
| 誤った価格が自動承認される | 列の取り違えで全グレードの価格が動く | 7.3 の変化率・絶対値・件数比の3つの歯止め |
| 販売中のグレードを誤って非公開にする | 抽出漏れを廃止と誤認する | `discontinued` を人間の承認に回す（7.3） |
| 巨大PDF・不正PDFを掴む | 費用の暴発、意図しない文書の読み込み | 6.1 の事前検査（10MB / 50ページ / Content-Type） |
| サイト構造の変更 | PDFリンクの位置が変わる | 見つからなければ「再登録が必要」として上げる。推測しない |

### 意図的に先送りする

| 項目 | 送り先 | 理由 |
|---|---|---|
| ヘッドレスブラウザでのサイトマップ巡回 | 別サブプロジェクト | まず登録方式で回し、新車種の取りこぼしが実際に問題になってから作る |
| トヨタ以外の8メーカー | 別サブプロジェクト | パイロットでPDFの差異を把握してから広げる |
| EVの電費を `wltc_mode` と共用するか | 別サブプロジェクト | km/L と Wh/km を同じ列に入れると並び替えと絞り込みが壊れる。<br>**先送りできるのは、パイロットからEVを外したからである**（3章）。EVを扱う時点で、専用列を足すか単位列を持つかを決める |
| `extra_features` のキー命名規約 | 実データ待ち | クロール結果に何が入るかを見てから決める |
| Citations による出典ページ記録 | 見送り | Structured Outputs と併用できない。`raw_output` の保存で代替する |
