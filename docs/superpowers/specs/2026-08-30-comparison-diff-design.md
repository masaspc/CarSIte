# 差分ハイライト 設計書

サブプロジェクト3「比較体験」の中核。**「この2台は何が違うのか」に直接答える。**

- ステータス: 承認済み（実装計画待ち）
- 前提となるもの: サブプロジェクト1（データ基盤）、サブプロジェクト2（収集パイプライン）

## 1. 解く問題

いまの比較表（`components/ComparisonTable.tsx`）は全項目を平等に並べる。

公開済みの実データで数えると、プリウス `Z(2.0L HV / FF)` と `Z(2.0L HV / 4WD)` の間で
**諸元15項目＋装備20項目のうち、実際に違うのは4項目だけ**である。

```
価格      ¥3,998,500  →  ¥4,251,500
駆動方式   FF          →  4WD
車両重量   1,420kg     →  1,480kg
燃費      28.4km/L    →  26.8km/L
```

残る31項目は同じ値である。利用者はそれを35行スクロールして探すことになる。

**比較の目的は「違いを知ること」であって「全項目を並べること」ではない。**

## 2. 方針

比較表の各行を「一致」か「相違」に分け、**既定では相違だけを見せる**。
切り替えで全項目に戻せる。

```
┌─────────────────────────────────────────┐
│ 違いのみ表示  ●━━━○  すべて表示          │
│ 35項目中 4項目が異なります                 │
├──────────┬─────────────┬────────────────┤
│ 価格      │ ¥3,998,500  │ ¥4,251,500     │
│ 駆動方式   │ FF          │ 4WD            │
│ 車両重量   │ 1,420kg     │ 1,480kg        │
│ 燃費      │ 28.4km/L    │ 26.8km/L       │
└──────────┴─────────────┴────────────────┘
```

「すべて表示」に切り替えたときは、相違行に色を付けて位置が分かるようにする。

**畳むのであって消すのではない。** 一致していることも情報なので、切り替えれば必ず見られる。

## 3. 一致判定は既存のものを使う

### 3.1 新しい比較ロジックを書かない

`pipeline/diff.ts` に `sameValue` という同値判定が既にある。

```ts
function sameValue(a: unknown, b: unknown): boolean
```

drizzle の numeric 列が文字列で返る問題（`wltc_mode` が `"26.0"`、抽出結果は `26`）を
吸収する規則で、収集パイプラインが差分検知に使っている。

比較表でも同じ規則を使えば、**「パイプラインが変更と見なすもの」と
「比較表が違いと見なすもの」が一致する。** 判定が2つに割れない。

### 3.2 現状は既に3箇所に散っている

調査したところ、`sameValue` は既に複製されていた。

| 場所 | 経緯 |
|---|---|
| `pipeline/diff.ts:116` | 原本 |
| `pipeline/apply.ts:429` | **複製。** タスクのファイル範囲を超えられない規約のため意図的に複製した |

比較表で3つ目を作れば、「同じ値とは何か」の定義が3箇所に散る。
numeric 列の扱いのような微妙な規則が3箇所にあるのは危うい。

**`lib/same-value.ts` に移し、3箇所すべてがそこを参照する形にする。**
この設計の副産物として既存の重複も解消される。

### 3.3 移設のリスク

`sameValue` は収集パイプラインの中核で、`computeChanges` と `applyChangeRequest` の
両方が依存する。移設は「切り取って貼る」だけだが、**既存テストが全て通ることを
確認してから進める**。振る舞いは1文字も変えない。

## 4. 何を比較対象にするか

`ComparisonTable` が既に描画している項目をそのまま使う。新しい項目は足さない。

実物を読んで確認した（`components/ComparisonTable.tsx`）。

| 群 | 項目 |
|---|---|
| 基本 | 価格、駆動方式、乗車定員 |
| 諸元 | 排気量、車両重量、燃費（WLTC）、市街地モード、高速道路モード、トランスミッション |
| 寸法 | 全長・全幅・全高（`dimensions` JSONB） |
| 性能 | 最高出力、最大トルク（`performance` JSONB） |
| 装備 | 20項目（`FEATURE_COLUMNS`） |

**`typeDesignation`（型式）と `powertrain` は現在の比較表に出ていない。**
どちらもグレードの同定に使う内部的な識別子で、利用者に見せる項目ではないと
判断されている。この設計でも足さない（8章「やらないこと」のとおり）。

### 4.0 表頭で同名グレードを見分けられない（実物で確認した欠陥）

`ComparisonTable` の表頭は `メーカー / 車種名 / グレード名` の3行だけである
（`components/ComparisonTable.tsx:157-159`）。

公開済みのプリウスには `Z` が3つ（PHEV/FF、HV/FF、HV/4WD）、`G` が3つある。
**この3つを並べると表頭が全部「トヨタ / プリウス / Z」になり、どの列がどれか分からない。**

差分ハイライトは「どこが違うか」を示すが、**そもそもどの列が何なのかが分からなければ
意味がない。** サブプロジェクト2で「同名グレード問題」を構造的に解決したのに、
比較画面でそれが可視化されていない。

**表頭に `powertrain` と駆動方式を足す。** これはこの設計の一部として扱う。

```
トヨタ                トヨタ                トヨタ
プリウス              プリウス              プリウス
Z                    Z                    Z
2.0L ハイブリッド車     2.0L ハイブリッド車     2.0L プラグインハイブリッド車
FF                   4WD                  FF
```

`typeDesignation`（型式）は足さない。同定はできるが利用者向けの情報ではなく、
`powertrain` と駆動方式があれば人間には十分区別できる。

### 4.1 装備は当面ほぼ全て一致する

**装備20項目のほぼ全てが `unknown` である。** 色でしか読めず、サブプロジェクト2で
先送りした（収集パイプライン設計書6.0）。

`unknown` 同士は一致と判定されるので畳まれ、実質的に諸元の差分だけが出る。
**現状ではこれが正しい振る舞いである。** 「装備が違う」という誤情報を出すより、
「分かっている範囲で違うのはここ」と言うほうが正確である。

装備を取り込んだ後は見え方が大きく変わる。そのときに再評価する。

### 4.2 `unknown` を「一致」と呼んでよいか

呼んでよい。ただし**画面上の表現には注意する。**

`ComparisonTable` は既に `unknown` を `−` と表示し、`×`（装備なし）と区別している。
「両方とも不明」を「一致」として畳むのは、**不明であることが同じ**という意味であり、
「同じ装備を持つ」という意味ではない。

そのため、畳んだ項目数を出すときは「35項目中4項目が異なります」とだけ言い、
「31項目が同じです」とは言わない。後者は誤読を招く。

## 5. 比較する台数

現在の `MAX_COMPARE` は3である。差分判定は**2台のときだけ**単純になる。

3台のときは「1台でも違えば相違」とする。これは「どれか1つでも異なる行を見せる」
という意味で、2台のときの定義と矛盾しない。

## 6. どこに置くか

| ファイル | 責務 |
|---|---|
| `lib/same-value.ts` | 同値判定。`pipeline/diff.ts` から移設 |
| `lib/comparison-diff.ts` | 比較行の組み立てと一致/相違の判定。純粋関数 |
| `components/ComparisonTable.tsx` | 描画。判定ロジックは持たない |
| `components/CompareListClient.tsx` | 切り替えの状態を持つ |

**判定と描画を分ける。** 判定を純粋関数にすれば、実データを使わず単体テストで固定できる。

## 7. テスト

| 対象 | 何を確かめるか |
|---|---|
| `lib/same-value.ts` | 移設前と同じ振る舞い（numeric 文字列、null、undefined） |
| `lib/comparison-diff.ts` | 一致/相違の判定、3台のときの扱い、`unknown` 同士が一致になること |
| 実データ | `Z(HV/FF)` と `Z(HV/4WD)` の相違が価格・駆動方式・重量・燃費の4項目になること |

実データの検証は公開済みの6グレードで行う。同名グレード（Z が3つ、G が3つ）と
駆動方式違いとパワートレイン違いが揃っており、題材として過不足がない。

## 8. やらないこと

- **最適グレード検索**（装備の組み合わせから最安を探す）。装備データが `unknown` の
  現状では成立しない。装備を取り込んでから別途設計する
- **差分の要約文**（「価格差 ¥253,000」等）。項目ごとに「安いほうが良い」「大きいほうが
  良い」といった意味づけが要り、それ自体が設計判断を含む。まず違いを見せることに絞る
- **比較表への項目追加**。既に描画している項目だけを対象にする

## 9. 完了条件

1. `npm run build` が ESLint 警告0で通り、単体・統合テストが全て通る
2. `sameValue` が `lib/same-value.ts` の1箇所だけになり、`pipeline/diff.ts` と
   `pipeline/apply.ts` がそれを参照している
3. 比較表が既定で相違行だけを表示し、切り替えで全項目に戻せる
3b. 表頭に `powertrain` と駆動方式が出て、同名グレード（プリウスの `Z` 3つ）を
   並べたときに列を区別できる
4. 相違行の数が画面に出る
5. 公開済みの実データで `Z(HV/FF)` と `Z(HV/4WD)` の相違が4項目になる
6. 3台比較で「1台でも違えば相違」が成立する
7. `unknown` 同士が一致として畳まれ、「31項目が同じ」という誤読を招く文言が無い
