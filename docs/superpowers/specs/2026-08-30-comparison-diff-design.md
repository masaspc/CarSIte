# 差分ハイライト 設計書

サブプロジェクト3「比較体験」の中核。**「この2台は何が違うのか」に直接答える。**

- ステータス: 承認済み（実装計画待ち）
- 前提となるもの: サブプロジェクト1（データ基盤）、サブプロジェクト2（収集パイプライン）

## 1. 解く問題

いまの比較表（`components/ComparisonTable.tsx`）は全項目を平等に並べる。

公開済みの実データで数えると、プリウス `Z(2.0L HV / FF)` と `Z(2.0L HV / 4WD)` の間で
**諸元20行＋装備20行の計40行のうち、実際に違うのは4行だけ**である。

```
価格      ¥3,998,500  →  ¥4,251,500
駆動方式   FF          →  4WD
車両重量   1,420kg     →  1,480kg
燃費      28.4km/L    →  26.8km/L
```

残る36行は同じ値である。利用者はそれを40行スクロールして探すことになる。

**比較の目的は「違いを知ること」であって「全項目を並べること」ではない。**

## 2. 方針

比較表の各行を「一致」か「相違」に分け、**既定では相違だけを見せる**。
切り替えで全項目に戻せる。

```
┌─────────────────────────────────────────┐
│ 違いのみ表示  ●━━━○  すべて表示          │
│ 40項目中 4項目が異なります                 │
├──────────┬─────────────┬────────────────┤
│ 価格      │ ¥3,998,500  │ ¥4,251,500     │
│ 駆動方式   │ FF          │ 4WD            │
│ 車両重量   │ 1,420kg     │ 1,480kg        │
│ 燃費      │ 28.4km/L    │ 26.8km/L       │
└──────────┴─────────────┴────────────────┘
```

「すべて表示」に切り替えたときは、相違行に色を付けて位置が分かるようにする。

**畳むのであって消すのではない。** 一致していることも情報なので、切り替えれば必ず見られる。

## 3. 一致判定は既存のものを使う

### 3.1 新しい比較ロジックを書かない

`pipeline/diff.ts` に `sameValue` という同値判定が既にある。

```ts
function sameValue(a: unknown, b: unknown): boolean
```

drizzle の numeric 列が文字列で返る問題（`wltc_mode` が `"26.0"`、抽出結果は `26`）を
吸収する規則で、収集パイプラインが差分検知に使っている。

比較表でも同じ規則を使えば、**DB表現上の差（`null`/`undefined`、`26` と `"26.0"`）の
扱いが2つに割れない。**

**ただし共有するのはそこまでである。** パイプラインの「変更判定」と比較UIの
「相違判定」は、全体として同じ概念ではない。UI側には製品上の意味が乗る。

- `unknown` を相違に含めるか（4.2で「含めない」と決めた）
- 空値の行を畳むか
- 表示用の単位を付ける前に比較するか（4.3で「付ける前」と決めた）

したがって `lib/same-value.ts` が担うのは**スカラーの同値判定だけ**で、
`unknown` の扱いのような製品判断は `lib/comparison-diff.ts` が持つ。
この境界を越えて共有しない。

### 3.2 現状は既に3箇所に散っている

調査したところ、`sameValue` は既に複製されていた。

| 場所 | 経緯 |
|---|---|
| `pipeline/diff.ts:116` | 原本 |
| `pipeline/apply.ts:429` | **複製。** タスクのファイル範囲を超えられない規約のため意図的に複製した |

比較表で3つ目を作れば、「同じ値とは何か」の定義が3箇所に散る。
numeric 列の扱いのような微妙な規則が3箇所にあるのは危うい。

**`lib/same-value.ts` に移し、3箇所すべてがそこを参照する形にする。**
この設計の副産物として既存の重複も解消される。

### 3.3 移設のリスク

`sameValue` は収集パイプラインの中核で、`computeChanges` と `applyChangeRequest` の
両方が依存する。移設は「切り取って貼る」だけだが、**既存テストが全て通ることを
確認してから進める**。振る舞いは1文字も変えない。

## 4. 何を比較対象にするか

`ComparisonTable` が既に描画している項目をそのまま使う。新しい項目は足さない。

実物を数えた（`components/ComparisonTable.tsx`、`renderRow` の呼び出し20件＋装備20項目）。
**合計40行**である。

| 群 | 項目 | 数 |
|---|---|---|
| 基本 | 価格、ボディタイプ、発売年月、乗車定員 | 4 |
| 寸法 | 全長、全幅、全高、車両重量 | 4 |
| エンジン | エンジンタイプ、総排気量、最高出力、最大トルク、トランスミッション、駆動方式 | 6 |
| 燃費 | WLTCモード、市街地モード、高速道路モード、航続可能距離 | 4 |
| その他 | エコカー減税、エアバッグ | 2 |
| 装備 | `FEATURE_COLUMNS` の20項目 | 20 |

**`typeDesignation`（型式）と `powertrain` は現在の比較表に出ていない。**
どちらもグレードの同定に使う内部的な識別子で、利用者に見せる項目ではないと
判断されている。行としては足さない（8章「やらないこと」のとおり）。
ただし表頭には出す（4.0）。

### 4.0 表頭で同名グレードを見分けられない（実物で確認した欠陥）

`ComparisonTable` の表頭は `メーカー / 車種名 / グレード名` の3行だけである
（`components/ComparisonTable.tsx:157-159`）。

公開済みのプリウスには `Z` が3つ（PHEV/FF、HV/FF、HV/4WD）、`G` が3つある。
**この3つを並べると表頭が全部「トヨタ / プリウス / Z」になり、どの列がどれか分からない。**

差分ハイライトは「どこが違うか」を示すが、**そもそもどの列が何なのかが分からなければ
意味がない。** サブプロジェクト2で「同名グレード問題」を構造的に解決したのに、
比較画面でそれが可視化されていない。

**表頭に `powertrain` と駆動方式を足す。** これはこの設計の一部として扱う。

```
トヨタ                トヨタ                トヨタ
プリウス              プリウス              プリウス
Z                    Z                    Z
2.0L ハイブリッド車     2.0L ハイブリッド車     2.0L プラグインハイブリッド車
FF                   4WD                  FF
```

`typeDesignation`（型式）は足さない。同定はできるが利用者向けの情報ではなく、
`powertrain` と駆動方式があれば人間には十分区別できる。

### 4.1 装備は当面ほぼ全て一致する

**装備20項目のほぼ全てが `unknown` である。** 色でしか読めず、サブプロジェクト2で
先送りした（収集パイプライン設計書6.0）。

`unknown` 同士は一致と判定されるので畳まれ、実質的に諸元の差分だけが出る。
**現状ではこれが正しい振る舞いである。** 「装備が違う」という誤情報を出すより、
「分かっている範囲で違うのはここ」と言うほうが正確である。

装備を取り込んだ後は見え方が大きく変わる。そのときに再評価する。

### 4.2 行の状態は三値である（`unknown` 混在の扱い）

**当初「一致」「相違」の二値で設計していたが、それでは足りない。**

装備は取り込みが先送りされているため、片方だけ既知という状態が起きる。

| 車A | 車B | 意味 |
|---|---|---|
| `standard` | `standard` | 確認できた一致 |
| `standard` | `none` | **確認できた相違** |
| `standard` | `unknown` | **相違ではない。車Bが不明なだけ** |
| `unknown` | `unknown` | 両方不明 |

3台目を取り込んだ後などに、一部だけ既知という状態は現実に起こる。
`standard` と `unknown` を「相違」に含めると、**装備が違うという誤情報**になる。

そこで行の状態を三値にする。

- **`same`** … 全ての値が同値
- **`different`** … 不明値を含まず、値が異なる
- **`unknown`** … 不明値を含むため判定できない

既定の「違いのみ表示」では `different` を出す。`unknown` は畳む
（不明であることを「違い」として見せない）。

**件数の文言も分ける。** 「40項目中4項目が異なります」は `different` の数だけを指す。
`unknown` を含む行があるときは「（うち N 項目は情報が不足しています）」を添える。
装備の取り込みが済めば `unknown` は消え、この但し書きも自然に出なくなる。

### 4.3 生値を比較し、表示は別に組み立てる

現行 `ComparisonTable` は比較前に表示用の文字列へ変換している。

- 価格 → `¥3,998,500`（`ComparisonTable.tsx:74`）
- 燃費 → 単位付き（同 78行）
- 乗車定員 → `5人`（同 178行）
- エコカー減税 → `対象` / `対象外`（同 199行）

`sameValue` は生値の比較を前提にしている。**表示文字列に適用すると、
numeric 文字列を吸収するという共有の理由そのものが成立しない**
（`"¥3,998,500"` は数値に落ちない）。

行の定義を次の3つに分ける。

```ts
interface ComparisonRowDef {
  label: string;
  /** 判定に使う生値。グレードごとに1つ */
  values: unknown[];
  /** セルに表示する文字列。整形はここでだけ行う */
  format: (value: unknown) => string;
}
```

**「表示してから比較」ではなく「生値を比較し、別途フォーマットする」。**

## 5. 比較する台数と、1台のときの扱い

現在の `MAX_COMPARE` は3である。台数ごとに挙動を定める。

| 台数 | 挙動 |
|---|---|
| 0台 | 現行どおり「比較する車両を選択してください」 |
| **1台** | **全項目を表示し、切り替えを無効にする。**「もう1台追加すると違いを表示できます」と案内する |
| 2台 | 既定は相違のみ |
| 3台 | 同上。1台でも値が違えば `different` |

**1台のときが要注意である。** 1台の値集合は全行が「一致」になるため、
既定の「違いのみ表示」では**表が空になり、故障のように見える**。
現行UIは1台でも比較画面を出す（`CompareListClient.tsx:37`）ので、この経路は実際に通る。

3台のときの `different` は「全ての値が同値でなければ相違」と定義する。
`A=A≠B`、`A≠B=A`、全て異なる、のいずれも相違になる。

## 6. どこに置くか

| ファイル | 責務 |
|---|---|
| `lib/same-value.ts` | 同値判定。`pipeline/diff.ts` から移設 |
| `lib/comparison-diff.ts` | 比較行の組み立てと一致/相違の判定。純粋関数 |
| `components/ComparisonTable.tsx` | 描画。判定ロジックは持たない |
| `components/CompareListClient.tsx` | 切り替えの状態を持つ |

**判定と描画を分ける。** 判定を純粋関数にすれば、実データを使わず単体テストで固定できる。

## 7. テスト

| 対象 | 何を確かめるか |
|---|---|
| `lib/same-value.ts` | 移設前と同じ振る舞い（numeric 文字列、null、undefined） |
| `lib/comparison-diff.ts` | 一致/相違の判定、3台のときの扱い、`unknown` 同士が一致になること |
| 実データ | `Z(HV/FF)` と `Z(HV/4WD)` の相違が価格・駆動方式・重量・燃費の4項目になること |

実データの検証は公開済みの6グレードで行う。同名グレード（Z が3つ、G が3つ）と
駆動方式違いとパワートレイン違いが揃っており、題材として過不足がない。

### 7.1 列の順序は既に保証されている（レビュー指摘の検証結果）

外部レビューで「`findPublishedGradesByRefs` に `ORDER BY` が無く、列順が
不定になる」との指摘があったが、**確認したところ対処済みだった。**

`app/actions/compare.ts` の `getComparisonGrades` が、DBから返った行を
`refs` の順に並べ直している（19〜29行目）。サブプロジェクト1で入れたものである。
この設計で追加の対応は要らない。

## 8. やらないこと

- **最適グレード検索**（装備の組み合わせから最安を探す）。装備データが `unknown` の
  現状では成立しない。装備を取り込んでから別途設計する
- **差分の要約文**（「価格差 ¥253,000」等）。項目ごとに「安いほうが良い」「大きいほうが
  良い」といった意味づけが要り、それ自体が設計判断を含む。まず違いを見せることに絞る
- **比較表への項目追加**。既に描画している項目だけを対象にする

### スモークテスト（補助）

公開済みの実データで次を確認する。**合否判定の本体ではない。**

対象は slug で一意に指定する（`Z` が3件あるため名前では指定できない）。

```
toyota/prius/z-20hv-ff  と  toyota/prius/z-20hv-4wd
  → 相違は 価格・駆動方式・車両重量・WLTCモード・市街地モード・高速道路モード
```

**注意:** 燃費は WLTC / 市街地 / 高速道路 の3行があるため、
1章で「4項目」と書いた見積もりは実際には増える可能性がある。
スモークテストでは件数を決め打ちせず、**上記の項目が相違に含まれること**を確認する。

### アクセシビリティ

切り替えUIは次を満たす。

- キーボードで操作できる
- 現在の状態が `aria-checked` またはテキストで分かる
- **相違を色だけで示さない。** 背景色は補助表現とし、「違いのみ表示」という
  絞り込みそのものと相違件数の表示を主要な手掛かりにする
